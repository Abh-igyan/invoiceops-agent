# EXP-001: Multi-Agent Decomposition, Deterministic Arithmetic Tools & OpenTelemetry Tracing (`v1` vs `v0`)

- **Date:** 2026-11-18
- **Phase:** P2 (`v1` Multi-Agent + OpenTelemetry Tracing)
- **Status:** Completed — **KEEP** (`v1` promoted as baseline for `v2`)
- **Related ADR:** [ADR-003](../decisions/003-multi-agent-decomposition-and-otel-tracing.md)

---

## 1. Hypothesis

Decomposing the monolithic single-agent `v0` baseline into a three-agent pipeline (`extraction_agent` $\rightarrow$ deterministic Python three-way match tool `compute_three_way_match` $\rightarrow$ `policy_rag_agent` $\rightarrow$ `orchestrator_agent` with ADK Tool Confirmation HITL), while **holding the policy retrieval index strictly constant** (`v0` naive 420-char fixed windows + plain cosine similarity), will:
1. Eliminate prose arithmetic and date-subtraction errors (`late_invoice_vs_terms`, `price_variance_within_tolerance`, `ambiguous_escalation`).
2. Raise escalation recall from `0.0%` to `100.0%` by wiring ADK's `ToolContext.request_confirmation` into `trigger_hitl_approval`.
3. Reduce cost-weighted error by $>80\%$ by eliminating unsafe false approvals (`10.0x` penalty weight) on late, stale-policy, and high-value escalation invoices.

## 2. Controlled Change (Single Variable Group)

| Dimension | `v0` Baseline | `v1` Multi-Agent (`EXP-001`) |

| **Observability** | Aggregate turn counters only | Root `invoiceops.resolve_invoice` span + child `agent.*` and `tool.*` OpenTelemetry spans |

---

## 3. Expected Effect

- **Outcome:** Decision accuracy increases by $+15\%$ to $+25\%$; cost-weighted error drops sharply from `~2.69` toward `<0.30` as false approvals on `late_invoice_vs_terms`, `ambiguous_escalation`, and `stale_policy_version` are eliminated.
- **Trajectory:** `ANY_ORDER` tool trajectory score reaches `1.000` because deterministic ERP verification (`lookup_vendor`, `check_invoice_history`, `lookup_purchase_order`, `lookup_goods_receipts`) is executed systematically after multimodal extraction.
- **Retrieval:** `Recall@5` and `MRR` improve moderately because `policy_rag_agent` formulates targeted queries from structured anomaly measurements rather than raw PDF prose, though superseded `V1` trap chunks remain in the index until `v2`.

## 6. Cost & Latency Impact

- **Live Spend:** `$0.00` (Google AI Studio Free Tier).
- **Shadow Paid-Tier Cost:** Increased from `$0.00314/case` to `$0.00412/case` (`+31.1%`) because 3 specialist agents execute `4.78` LLM calls per case (vs `2.80` in `v0`) and pass pretty-printed JSON payloads between `policy_rag_agent` and `orchestrator_agent`. This motivates `v3` (`EXP-003`) model routing and prompt trimming.
- **Latency:** `p95` latency improved by `-17.8%` (`44.26s` $\rightarrow$ `36.39s`) because binary PDF bytes are sent only once to `extraction_agent` instead of being re-sent on every tool-calling turn.

---

## 7. Decision & What I Learned

- **Decision:** **KEEP `v1`** as the multi-agent foundation for Phase P3 (`v2`–`v4`).
- **Key Lessons:**
  1. **Moving math out of LLM prose eliminates high-cost false approvals:** In `v0`, the model repeatedly miscalculated 105-day GRN delays and $17k approval thresholds in prose, causing `10x`-cost false approvals (`weighted_error = 2.694`). Moving three-way match math into `compute_three_way_match` cut cost-weighted error by **93.8%** (`0.167`).
  2. **Why `citation_validity_rate` dipped (`91.7%` $\rightarrow$ `83.3%`) and why `v2` + `v4` are needed:** Inspecting `results/eval_runs.jsonl` showed two concrete failure modes remaining in `v1`: (a) naive 420-char chunks still surface superseded `-V1#` clauses in `41.7%`–`50.0%` of cases and split multi-clause rules (`INV-4002` clean match missed `POL-03#1` in Run 1), and (b) when the Orchestrator wraps a long explanation across lines inside a JSON string, `json.loads` fails with `SCHEMA_VALIDATION_FAILED` (producing empty citations `[]`) or the model cites the invoice's own ID (`INV-4301`) as an `erp_record`.
